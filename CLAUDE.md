# CLAUDE.md — Sav waitlist landing

This file gives Claude Code context when it opens this repo.

## What this is

A single-page Next.js 16 marketing site for **Sav**, a parenting-coach
waitlist. Yetty Williams (founder of LagosMums) routes traffic to this
site from her other properties. Visitors enter an email + optional
details and join the waitlist. After signing up, they see a WhatsApp
CTA so Yetty can talk to the first cohort directly.

## Architecture

- **Next.js 16 App Router**, **React 19**, **Tailwind CSS 4**
- Entire homepage is `src/app/page.tsx` (a `"use client"` component;
  sections are co-located helper functions)
- Every "Join the waitlist" CTA opens `WaitlistDialog`
  (`src/components/ui/dialog.tsx`). The flow is **email-first**: the email
  is captured and saved immediately (one field, low friction), then the
  success screen offers **optional enrichment** (WhatsApp number,
  children's ages, top digital concerns) alongside the founding-member
  badge and invite. It remounts on each open (via a `key`) so state
  resets.
- The modal posts JSON to the `POST /api/waitlist` route handler
  (`src/app/api/waitlist/route.ts`) — a stable endpoint (not a hashed
  Server Action) so submissions survive redeploys. It validates with the
  shared zod schema in `src/lib/waitlist.ts` (fields: `email`, `phone`,
  `childrenAges`, `referralSource`, `digitalConcerns`; plus a `website`
  honeypot). The first call **inserts** the email into `sav_waitlist`; a
  second `mode: "enrich"` call **updates** that row by email with whatever
  optional fields were provided (never clearing earlier answers), via the
  server-only client in `src/lib/supabase.ts` (service role). Duplicate
  emails (Postgres `23505`) are surfaced as a friendly success.
- All swappable links/copy live in `src/lib/config.ts`. Env vars override:
  `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_WHATSAPP_URL`
- SEO assets are generated by Next conventions:
  - `src/app/icon.tsx` — favicon (dynamic SVG → PNG)
  - `src/app/apple-icon.tsx` — touch icon
  - `src/app/opengraph-image.tsx` — share preview (1200×630)
  - `src/app/twitter-image.tsx` — re-exports the OG image
  - `src/app/robots.ts`, `src/app/sitemap.ts`
- `next.config.ts` sets security headers (CSP, HSTS, X-Frame-Options,
  etc.), disables `x-powered-by`, redirects `/sav` → `/` and
  `/favicon.ico` → `/icon`
- Analytics: Vercel Web Analytics (`<Analytics/>` in `layout.tsx`) for
  pageviews, plus a funnel of our own — `src/lib/track.ts` fires
  `page_view`/`modal_opened`/`step_completed`/`signup_completed` to
  `POST /api/track`, stored in the `sav_events` Supabase table.
- Abuse hardening: `/api/waitlist` and `/api/track` enforce content-type
  + body-size checks and a Postgres fixed-window rate limit
  (`check_rate_limit` RPC, `sav_rate_limit` table) via `src/lib/rate-limit.ts`.
- Email (best-effort, **setup unfinished — see TODO below**): on a
  successful signup, `src/lib/email.ts` sends a welcome email to the
  signup + an optional notification to the team via Resend. No-op until
  `RESEND_API_KEY` + `EMAIL_FROM` are set, so signups work without it.
- New Supabase objects need their SQL applied: migrations `0002` (phone +
  referral) and `0003` (events + rate limiter) under `supabase/migrations/`.

## Supabase

Already wired (`@supabase/supabase-js` installed, the `/api/waitlist`
route inserts on submit). To connect a database:

1. Run `supabase/sav_waitlist.sql` in the Supabase SQL editor
2. Set `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` env vars (locally in
   `.env.local`, in production via Vercel)

`getSupabaseAdmin()` returns `null` when those vars are unset, and the
route fails closed with a generic error rather than dropping signups.

  The live site's `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` point at
  project `wmuxpcqjhaxbqtphazot` (Vercel Storage → "supabase-fulvous-
  helmet"). It is **free-tier and auto-pauses after ~7 days idle** — when
  it sleeps, live signups 500 (`ENOTFOUND …supabase.co`) *and* Vercel
  builds die at "Provisioning integrations failed". Fix = wake it via
  "Open in Supabase" (it returns to Healthy). **Permanent fix = upgrade
  that project to Supabase Pro** so it never pauses. (Still outstanding.)
- The only Supabase project reachable from the MCP tools is a *different*
  one, "YettyAI Project" (`jbuwvbjjjrhwbszanpma`, the chat app's DB). The
  `sav_*` tables were created there as a spare, but **production does not
  use it**. Any schema change to production must be done by the user in
  the Supabase SQL editor — the MCP can't reach `wmuxpcqjhaxbqtphazot`.
- **Pending prod SQL** (run in the `wmuxpcqjhaxbqtphazot` SQL editor to
  enable the "top digital concerns" capture):
  `alter table public.sav_waitlist add column if not exists digital_concerns text[];`
  Until it runs, the API safely drops `digital_concerns` (retries the
  enrich without that column), so signups never break.

## Deploy & verify workflow

- Develop on branch `claude/cool-pascal-voxzuc`. Each push builds a
  **preview** at the branch alias
  `sav-waitlist-git-claude-cool-pascal-voxzuc-yetty-4518s-projects.vercel.app`.
- Production deploys from `main` (alias `sav-waitlist.vercel.app`).
  "Ship it" = open a PR from the branch and merge to `main`.
- Before each commit: `cp src/app/page.tsx sav-clone/src/app/page.tsx`
  (sync the saved copy — see below; also sync `route.ts`/`waitlist.ts`
  when they change), then `npx tsc --noEmit` and `npm run lint` must pass.
  **Commit promptly** — the web container can be reclaimed mid-session and
  uncommitted edits are lost; if `node_modules` is missing after a reset,
  run `npm ci`.
- `sav-clone/` is a standalone, deployable **saved copy** of the site,
  kept in sync with the shipped version. It's excluded from the root
  TypeScript/ESLint config so it never affects the production build.

## Product vision (the "why")

Sav is a "third parent": a non-judgemental, always-on coach for raising
kids in the digital age (screen time, AI, online safety), distilled from
Yetty Williams (founder of LagosMums, Yale MBA, trained in
cyberpsychology). The waitlist is a **growth + validation engine**:

- Goal: **1,000 signups** (email + first name + WhatsApp) as proof of
  demand for fundraising/launch.
- Joiners become **founding members of "Mums Training AI"**, an exclusive
  club; the post-signup badge + "Invite other parents" share turn them
  into ambassadors. WhatsApp is where the first cohort helps *shape* Sav.
- Roadmap: trackable referral links/leaderboard, first-name capture, a
  live "X of 1,000" counter, downloadable badge image, then events/merch.

## Copy & brand conventions

- Spelling: use **"mums"** (British), not "moms". Invites are phrased
  inclusively as **"parents"** (e.g. the "Invite other parents" button),
  while the club brand stays **"Mums Training AI"**.
- **No em dashes (—)** in user-facing copy — use commas, colons, or
  periods. (Hyphens in compound words like "judgement-free" are fine.)
- The WhatsApp perk = the chance to **personalize Sav and help shape what
  it becomes**, not a generic "thank you".
